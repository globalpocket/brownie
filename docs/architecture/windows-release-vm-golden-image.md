# Windows release VM golden image

This document defines the reusable Windows image baseline for Brownie local
release runners.

## Scope

The Windows VM is used to produce and smoke-test the `win32-x64` Brownie CLI
artifact without hosted CI services.

## Initial setup checklist

1. Create the local QEMU disk and launch command from the Brownie workspace.
2. Install Windows 11 Pro from Microsoft official media.
3. Activate with the owner-purchased Windows 11 Pro license.
4. Create a dedicated runner user, for example `brownie`.
5. Enable OpenSSH Server.
6. Allow SSH through Windows Firewall.
7. Add the Mac control-host SSH public key to the runner user's
   `authorized_keys`.
8. Install Git, Node.js LTS, Rustup, and pnpm/Corepack, or let
   `release:vm-bootstrap` install them with `winget` after SSH works.
9. Verify from the Mac:

   ```sh
   ssh brownie-windows powershell -NoProfile -Command '$PSVersionTable.PSVersion'
   ```

10. Create a VM snapshot or golden image before cloning Brownie or generating
   release artifacts.

Brownie can manage the local image lifecycle once the runner is reachable:

```sh
pnpm release:vm-image -- --action status --target windows
pnpm release:vm-image -- --action shutdown --target windows
pnpm release:vm-image -- --action snapshot --target windows
pnpm release:vm-image -- --action start --target windows
```

The snapshot command writes ignored local image state under
`.brownie/private/vm-images/windows/brownie-windows-arm64-golden/` by default. It refuses
to snapshot while QEMU is still running so the `qcow2`, EDK2 variable store, and
TPM state remain consistent.

## Create the QEMU VM shell

Brownie can create the reusable local disk, register the `win32-x64` release
target, and print the SSH config/launch command:

```sh
pnpm release:windows-vm-create -- --dry-run --iso /path/to/Win11.iso
pnpm release:windows-vm-create -- --iso /path/to/Win11.iso
```

On Apple Silicon, prefer a Windows 11 Arm64 ISO and an ARM64/HVF VM:

```sh
pnpm release:windows-vm-create -- \
  --vm-arch arm64 \
  --iso /path/to/Win11_Arm64.iso \
  --display vnc \
  --launch
```

The ARM64 runner still registers the Brownie artifact target as `win32-x64`;
the runner architecture is tracked separately as `runner_arch`. Install the x64
Windows toolchain inside the VM when producing and smoke-testing the `win32-x64`
artifact under Windows on Arm x64 emulation. Brownie's local artifact builder
uses Rust's `x86_64-pc-windows-msvc` target through Visual Studio Build Tools
when it is asked to produce `win32-x64` from a `win32/arm64` runner, then
smoke-tests the generated x64 `brownie.exe` under Windows on Arm.

The x64 fallback uses local QEMU x86_64 TCG emulation with `-cpu max`, a
Windows-standard SATA/AHCI system disk, user-mode networking, and a fixed SSH
forward. The ARM64 path uses QEMU `virt` with HVF, NVMe system disk, VNC,
software TPM, VirtIO networking, and the same SSH forward:

```sshconfig
Host brownie-windows
  HostName 127.0.0.1
  Port 2222
  User brownie
  IdentityFile ~/.ssh/brownie_release_runner
  IdentitiesOnly yes
```

To launch the installer directly:

```sh
pnpm release:windows-vm-create -- --iso /path/to/Win11.iso --launch
```

If the QEMU Cocoa window is not visible from the automation environment, launch
with VNC display and open the printed `vnc://...` URL from macOS Screen Sharing:

```sh
pnpm release:windows-vm-create -- --iso /path/to/Win11.iso --display vnc --launch
```

The default local VNC password is `brownie`; override it with
`--vnc-password` if needed. The VNC listener is bound to `127.0.0.1` by default.
The launcher also creates a QEMU monitor socket at
`.brownie/private/vms/brownie-windows/qemu-monitor.sock`, which lets automation send
bounded keys such as `sendkey ret` during installer boot.
Use `--no-reboot` only for troubleshooting boot loops; normal installation
should allow Windows setup to reboot the VM.

On Apple Silicon, Windows 11 Arm64 does not reliably recognize QEMU `e1000`,
`e1000e`, or `usb-net` as an inbox network adapter. Use the VirtIO network
device generated by `release:windows-vm-create` and install the signed
`NetKVM/w11/ARM64/netkvm.inf` driver from the stable `virtio-win.iso` before
expecting SSH or `winget` to work. A practical local flow is:

1. boot once with a temporary inbox or no-network adapter;
2. attach `virtio-win.iso`;
3. in an elevated PowerShell, run:

   ```powershell
   pnputil /add-driver E:/NetKVM/w11/ARM64/netkvm.inf /install
   ```

4. shut down the VM;
5. relaunch with the generated `virtio-net-pci` NIC;
6. verify that the guest can reach the network and that Mac SSH forwarding to
   `127.0.0.1:2222` works.

Windows installation and activation remain owner-controlled because they involve
the licensed installer UI and product key/account decisions. After SSH works,
Brownie can run the fixed bootstrap and artifact commands without additional
manual steps.

## PowerShell setup commands

Run in an elevated PowerShell session inside the Windows VM:

```powershell
$ErrorActionPreference = 'Stop'

Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Set-Service -Name sshd -StartupType Automatic
Start-Service sshd

if (-not (Get-NetFirewallRule -Name OpenSSH-Server-In-TCP -ErrorAction SilentlyContinue)) {
  New-NetFirewallRule `
    -Name OpenSSH-Server-In-TCP `
    -DisplayName 'OpenSSH Server (sshd)' `
    -Enabled True `
    -Direction Inbound `
    -Protocol TCP `
    -Action Allow `
    -LocalPort 22
}

winget install --id Git.Git -e --accept-source-agreements --accept-package-agreements
winget install --id OpenJS.NodeJS.LTS -e --accept-source-agreements --accept-package-agreements
winget install --id Rustlang.Rustup -e --accept-source-agreements --accept-package-agreements
winget install `
  --id Microsoft.VisualStudio.2022.BuildTools `
  -e `
  --accept-source-agreements `
  --accept-package-agreements `
  --override "--quiet --wait --norestart --nocache --installPath C:\BuildTools --add Microsoft.VisualStudio.Workload.VCTools --add Microsoft.VisualStudio.Component.VC.Tools.ARM64 --add Microsoft.VisualStudio.Component.VC.Tools.x86.x64 --add Microsoft.VisualStudio.Component.Windows11SDK.26100 --includeRecommended"

corepack enable
corepack prepare pnpm@9.0.0 --activate
```

If `Add-WindowsCapability` hangs or the `sshd` service is still absent after it
returns, use the ARM64 MSI from the official PowerShell/Win32-OpenSSH release
instead. A controlled local setup can download the MSI on the Mac, serve it to
the VM over a temporary loopback-bound HTTP server, and run `msiexec` inside the
VM. Keep the MSI filename and SHA-256 in local setup evidence so the golden
image remains reproducible.

Add the Mac public key for the runner user:

```powershell
$SshDir = Join-Path $env:USERPROFILE '.ssh'
New-Item -ItemType Directory -Force -Path $SshDir | Out-Null
notepad (Join-Path $SshDir 'authorized_keys')
icacls $SshDir /inheritance:r
icacls $SshDir /grant "$env:USERNAME:(OI)(CI)F"
icacls (Join-Path $SshDir 'authorized_keys') /inheritance:r
icacls (Join-Path $SshDir 'authorized_keys') /grant "$env:USERNAME:F"
```

```sshconfig
Host brownie-windows

  Port 2222
  User brownie
  IdentityFile ~/.ssh/brownie_release_runner
  IdentitiesOnly yes
```

## Restore flow

After restoring the golden image:

```sh
pnpm release:vm-bootstrap -- --target win32-x64
pnpm release:local-artifacts:all
pnpm release:supply-chain-artifact-evidence
pnpm guard:supply-chain-artifact-evidence
```

Restore itself is intentionally not automatic because it replaces VM disk state.
Stop QEMU first, copy the selected `.brownie/private/vm-images/windows/<snapshot>/`
contents back to `.brownie/private/vms/brownie-windows-arm64/`, start the VM, and rerun
the commands above.
